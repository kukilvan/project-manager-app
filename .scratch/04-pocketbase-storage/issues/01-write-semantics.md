# 01. Write semantics and rules (the pure module)

What a write means and who may do it, as one pure module that runs unchanged on the phone and inside PocketBase. No server, no screen, no change to the site.

## Spec sections

§ 2.2, § 2.3, § 2.4 (ops, rules table, answers), § 2.7 (generation, `PB_SCHEMA`), § 10 (edge cases 1, 16, 18, 23, 26), § 11 (the pure tests of `pbwrite`), § 12 (rule 15, term «Schema version»). Slicing notes under § 13 apply.

## What to do

1. `src/domain/pbwrite.js`, with a header comment. Syntax PocketBase's JS engine runs: no `?.`, no `??`, no imports, plain functions, `export` only for the generator to turn into `module.exports`. Contents:
   - constants: `PB_SCHEMA = 1`, `MIN_CLIENT_SCHEMA = 1`, `POOL_KINDS` (§ 2.1), the limits (project `key` ≤ 64, record `key` ≤ 400, `coll` `^[A-Za-z]{1,40}$`, at most 500 ops);
   - `toOps(kind, pid, writes)`: the writes of `commit`, `commitPool`, `setInbox`, `allowEmails` and `saveUserPrefs` (shapes in `createFirestoreBackend`, `src/app/repo.js`) into the ops of § 2.3: `project` (`fields` when the write has `replace`, else `deep`; `arrayOps`), `rec` (`fields` for `points` and `replace`), `history` (create only), `pool` (`remove` → `{deleted: true}`), `inbox`, `allowed`, `prefs`. `updatedAtServer` is dropped. Walk every call of `createRepo` that ends in a write (`save`, `remove`, `restore`, `createProject`, `saveProject` with and without `arrayOps`, `savePool`, `setInbox`, `allowEmails`, `saveUserPrefs`, `retryRejected`) and cover each shape;
   - the merges of § 2.3: `mergeDeep` (Firestore `merge: true`: objects merge key by key, arrays and scalars and `null` replace, an empty object replaces), `mergeFields` (`mergeFields: Object.keys(data)`), `applyArrayOps` (`union` appends missing values in order, `remove` drops every equal value), `applyItemPatches` (jobs), and `mergeDoc(old, op)` that returns the document to save (a missing target is created from the write);
   - the rules of § 2.4 as `checkOp(env, op, oldDoc, newDoc)` → `{ok: true}` or `{ok: false, code, message}` with code `forbidden`, `not-found` or `invalid`. `env` = `{user: {id, email}, isSuper, adminEmail, isAllowed(email), project(pid)}` where `project(pid)` gives the project as of this point of the request. "Changes" = a top-level key differs between old and merged (deep compare, as Firestore's `diff().affectedKeys()`); e-mails compared in lower case. `validateOp` covers a bad op, an unknown pool kind, a bad collection name, a too long key;
   - `runSave(store, env, request)`: the whole route logic over a small `store` object (`find(target)`, `put(target, doc)`, a `begin/commit/rollback` or copy-on-write pair): schema check (409 `schema_old`, 426 `app_old`), ops in order, projects loaded once and reused so a later op sees an earlier one, the first refusal stops the request and nothing of it is kept (answer `{status, code, index, message}`), the `invites` list to keep in step with `invitedEmails` (`invitesOf(project)` → `{email, name, object, from}`), `members` ids from `memberUids`. The hook of ticket 02 supplies a PocketBase store and the transaction; the tests supply a map. Keep the hook thin — all decisions live here.
2. `scripts/pb-hooks-build.mjs`: writes `pb/pb_hooks/pm/pbwrite.js` from `src/domain/pbwrite.js` (`export` → `module.exports`, a first line «GENERATED by scripts/pb-hooks-build.mjs — do not edit»); `--check` changes nothing and exits 1 when the file is stale. Add `"pb:hooks": "node scripts/pb-hooks-build.mjs"` to `package.json`. Commit the generated file (like `src/i18n/en.json`).
3. Docs: `docs/coding-standards.md` rule 15 (the generated hook module is never edited by hand; a test fails when it is stale — reason and check as the other rules); `CONTEXT.md` term «Schema version» (`PB_SCHEMA`, the server's number; «server older» is explained by ticket 08).
4. Header comments of the two new modules; `node tools/code-map.mjs`.
5. Self-check: tests, `npm run build`; the built `dist/assets` file names are the same as before (nothing imports the module yet).
